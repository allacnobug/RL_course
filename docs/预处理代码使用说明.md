# 预处理代码使用说明

本文档说明 `src/preprocess.py`、`src/build_events.py`、`src/features.py`、`src/baselines.py`、`src/env.py`、`src/models.py`、`src/train.py`、`src/evaluate.py` 和 `src/plot_curves.py` 的作用、运行方式、输出文件和后续使用方法。

## 0. Conda 环境部署

### 0.1 使用 environment.yml 创建环境

建议使用 Python 3.10 或 3.11。`preprocess.py` 和 `build_events.py` 只依赖 Python 标准库；`features.py` 需要 `numpy`。

本项目已经提供 Conda 环境文件：

```text
environment.yml
```

第一次使用时，在项目根目录运行：

```bash
conda env create -f environment.yml
conda activate rl-course
```

如果之后修改了 `environment.yml`，可以更新已有环境：

```bash
conda env update -f environment.yml --prune
conda activate rl-course
```

验证环境：

```bash
python --version
python -c "import numpy; print(numpy.__version__)"
python -c "import torch; print(torch.__version__)"
```

### 0.2 environment.yml 里包含什么

当前 `environment.yml` 包含：

```text
python=3.10
numpy
pandas
matplotlib
scikit-learn
tqdm
pytorch

```

其中：

```text
pandas：后续表格分析可用
```

### 0.3 如果环境创建失败

如果 `conda env create -f environment.yml` 失败，优先检查：

```text
1. 是否已经安装 conda 或 miniconda。
2. 是否在项目根目录运行命令。
3. 是否已经存在同名 rl-course 环境。
```

如果已经存在同名环境，可以先更新：

```bash
conda env update -f environment.yml --prune
```

或者删除后重建：

## 1. 这个脚本做什么

`src/preprocess.py` 是整个强化学习推荐实验的第一步。它负责把老师给的原始数据整理成后续代码容易读取的结构化 CSV。

`src/build_events.py` 是第二步。它负责把提交记录按时间排序，构造强化学习推荐事件，并划分训练集、验证集、测试集。

`src/features.py` 是第三步。它负责把推荐事件转换成 DQN 可以直接读取的数值特征张量。

`src/baselines.py` 是第四步。它负责评估规则推荐方法，给后续 DQN 实验提供对比基线。

`src/env.py` 是第五步。它负责把 `.npz` 特征包封装成 DQN 训练可以使用的 `reset/step` 环境。

`src/models.py` 是第六步。它负责定义 DQN / Double DQN / Dueling DQN 的神经网络结构。

`src/train.py` 是第七步。它负责训练 DQN 系列模型，保存训练曲线日志和 checkpoint。

`src/evaluate.py` 是第八步。它负责把训练好的 checkpoint 在验证集或测试集上统一评估。

`src/plot_curves.py` 是第九步。它负责画训练曲线和方法对比图。

原始数据包括：

```text
data/project_list.csv
data/worker_quality.csv
data/project/project_*.txt
data/entry/entry_*.txt
```

脚本输出：

```text
outputs/processed/project.csv
outputs/processed/entry.csv
outputs/processed/worker.csv
outputs/processed/industry_map.json
outputs/processed/stats.json
outputs/processed/events_train.csv
outputs/processed/events_valid.csv
outputs/processed/events_test.csv
outputs/features/train_features.npz
outputs/features/valid_features.npz
outputs/features/test_features.npz
outputs/tables/baseline_results_test.csv
```

后续的事件构造、特征工程、强化学习环境、DQN 训练都基于这些输出文件。

## 2. 为什么要先做预处理

原始数据是 CSV 加大量 JSON 文本文件。如果直接在训练代码里读取，会有几个问题：

1. 字段分散，project、entry、worker 信息不好关联。
2. 时间字段、缺失字段、布尔字段格式不统一。
3. 每次训练都重新读大量 JSON 文件，速度慢，也不方便排查错误。
4. 无法清楚统计数据规模、缺失情况和异常情况。

因此先统一清洗成三张表：

```text
project.csv：每一行是一个任务 project
entry.csv：每一行是一个 worker 对 project 的提交
worker.csv：每一行是一个 worker 及其 quality
```

## 3. 第一步：运行数据预处理

在项目根目录运行：

```bash
python3 src/preprocess.py \
  --data_dir data \
  --output_dir outputs/processed
```

如果想让脚本遇到错误文件就立刻停止，可以加 `--strict`：

```bash
python3 src/preprocess.py \
  --data_dir data \
  --output_dir outputs/processed \
  --strict
```

一般情况下不需要 `--strict`。默认模式会跳过解析失败的文件，并把错误样例写入 `stats.json`。

## 4. 第二步：构造推荐事件

预处理成功后，运行：

```bash
python3 src/build_events.py \
  --processed_dir outputs/processed \
  --output_dir outputs/processed \
  --candidate_size 20 \
  --train_ratio 0.70 \
  --valid_ratio 0.15 \
  --seed 42
```

输出文件：

```text
outputs/processed/events_train.csv
outputs/processed/events_valid.csv
outputs/processed/events_test.csv
outputs/processed/events_stats.json
```

### 4.1 build_events.py 做了什么

它会执行以下步骤：

```text
1. 读取 project.csv、entry.csv、worker.csv。
2. 按 entry_created_at 对所有提交排序。
3. 每条 entry 视作一次 worker 到达事件。
4. 当前 entry 对应的 project 是正样本 positive_project。
5. 在该时间点维护 active project 集合。
6. 从 active projects 中采样 K-1 个负样本。
7. 将 1 个正样本和 K-1 个负样本打乱，形成候选集。
8. 按时间顺序划分 train / valid / test。
```

默认候选集大小：

```text
K = 20
```

也就是每个事件包含：

```text
1 个真实选择 project
19 个同一时间 active 的负样本 project
```

### 4.2 events_train.csv / events_valid.csv / events_test.csv 字段

主要字段：

```text
event_id                事件编号
split                   train / valid / test
event_time              worker 到达时间，这里用 entry_created_at 近似
worker_id               当前 worker
positive_project_id     历史真实提交 project
candidate_project_ids   候选 project 列表，用 | 分隔
label_index             positive_project 在候选列表中的位置
active_project_count    当前时间点 active project 数量
entry_id                原始 entry id
entry_number            project 内部 entry 编号
winner                  该 entry 是否 winner
finalist                该 entry 是否 finalist
withdrawn               该 entry 是否 withdrawn
award_value             获得奖金
offer_value             offer 金额
tip_value               小费
score                   entry 最高 revision score
normalized_score        score / 5
is_entirely_original    是否原创
worker_quality          worker 质量
quality_unknown         worker quality 是否未知
```

### 4.3 为什么这样构造事件

老师要求模拟：

```text
任务创建时间、到期时间、worker 到达时间
```

所以事件构造时使用：

```text
project.start_date <= event_time <= project.deadline
```

来判断某个 project 在当前时刻是否可推荐。

历史中 worker 实际提交的 project 被视为正样本。这相当于在离线数据中模拟：

```text
如果系统当时推荐了这个 project，worker 很可能会参与。
```

### 4.4 如果 active project 不够怎么办

默认情况下，如果某个时间点 active project 不足以采样 K-1 个负样本，该事件会被跳过。

如果想强行保留这些事件，可以加：

```bash
python3 src/build_events.py \
  --processed_dir outputs/processed \
  --output_dir outputs/processed \
  --candidate_size 20 \
  --allow_fallback_negatives
```

这会从所有 project 中补足负样本。但主实验建议不要开启，因为它会引入非 active project，和真实推荐场景不完全一致。

### 4.5 events_stats.json

这个文件记录事件构造统计：

```text
candidate_size
seed
train_ratio
valid_ratio
test_ratio
project_count
project_with_valid_window_count
entry_count_after_basic_filter
event_count
train_event_count
valid_event_count
test_event_count
skipped_insufficient_negatives
skipped_time_parse
allow_fallback_negatives
```

可以把这些统计写进报告的数据处理部分。

## 5. 第三步：构造 DQN 特征

事件构造完成后，运行：

```bash
python3 src/features.py \
  --processed_dir outputs/processed \
  --output_dir outputs/features
```

如果只是测试代码是否能跑通，可以先抽样：

```bash
python3 src/features.py \
  --processed_dir outputs/processed \
  --output_dir outputs/features_debug \
  --max_events_per_split 100
```

输出文件：

```text
outputs/features/train_features.npz
outputs/features/valid_features.npz
outputs/features/test_features.npz
outputs/features/feature_names.json
outputs/features/features_stats.json
```

### 5.1 features.py 做了什么

它会执行以下步骤：

```text
1. 读取 project.csv 和 events_train/valid/test.csv。
2. 按时间顺序扫描所有 event。
3. 对每个 event 的 20 个 candidate project 分别构造特征。
4. 在构造当前 event 特征之前，只使用过去历史统计 worker/project 信息。
5. 当前 event 处理完成后，再更新 worker 历史和 project 历史。
6. 为每个 candidate project 计算 worker_reward 和 requester_reward。
7. 保存为 DQN 训练可直接读取的 npz 文件。
```

这个顺序很重要，因为它避免了未来信息泄漏。

### 5.2 npz 文件里有什么

每个 split 的 `.npz` 文件包含：

```text
states                 shape = [num_events, 20, feature_dim]
labels                 shape = [num_events]
worker_rewards         shape = [num_events, 20]
requester_rewards      shape = [num_events, 20]
event_ids              shape = [num_events]
worker_ids             shape = [num_events]
positive_project_ids   shape = [num_events]
candidate_project_ids  shape = [num_events, 20]
```

其中：

```text
states[i, j, :] 表示第 i 个事件中第 j 个 candidate project 的特征。
labels[i] 是真实 positive project 在 20 个候选项目中的位置。
worker_rewards[i, j] 是选择第 j 个候选项目时的参与者利益 reward。
requester_rewards[i, j] 是选择第 j 个候选项目时的请求者利益 reward。
```

### 5.3 当前特征包括什么

当前每个 worker-project pair 有 35 维特征，主要包括：

```text
worker_quality
worker 历史提交数
worker 历史平均 score
worker 历史 winner/finalist/withdrawn 比率
worker 历史平均 award

project category/sub_category/industry
project 奖金、预计回答数、总提交数、平均分
project 是否 featured/assured/private_gallery
project 持续时间

当前时间下的 project_age_ratio
当前时间下的 project_time_left_ratio
当前时间前 project 已有提交数和平均质量

worker 与 project 的 category/industry 是否匹配
worker 对该 category/industry 的历史偏好比例
worker 过去是否做过该 project
当前 active project 数量
```

完整特征名保存在：

```text
outputs/features/feature_names.json
```

### 5.4 reward 保存在哪里

`features.py` 同时保存两套 reward：

```text
worker_rewards
requester_rewards
```

后续训练时可以通过参数选择：

```text
--reward_type worker
--reward_type requester
```

这样可以用同一套 state，对比两个不同优化目标。

### 6.1 当前包含哪些 baseline

```text
random              随机选择一个候选 project
popular             选择当前历史提交数最多的 project
award               选择奖金最高的 project
deadline            选择最接近截止时间的 project
category_match      选择与 worker 历史 category/industry 偏好最匹配的 project
oracle_worker       理论上限：直接选择 worker_reward 最大的 project
oracle_requester    理论上限：直接选择 requester_reward 最大的 project
```

注意：

```text
oracle_worker 和 oracle_requester 不是可部署方法，因为它们使用了真实 reward。
它们只用于汇报中展示 reward 设计下的理论上限。
```

### 6.2 baseline 输出指标

结果表包含：

```text
hit_at_1                推荐是否命中真实提交 project
avg_worker_reward       平均参与者 reward
avg_requester_reward    平均请求者 reward
avg_total_reward        两类 reward 之和
category_match_rate     category 匹配率
industry_match_rate     industry 匹配率
avg_worker_quality      被推荐 worker 的 quality
project_coverage        推荐覆盖的 project 比例
unique_recommended_projects 推荐过的 project 数量
reward_std              reward 标准差
```

这些结果可以直接放进报告和 PPT 的 baseline 对比部分。

## 7. 第五步：测试强化学习环境

`src/env.py` 提供一个轻量环境类：

```python
from src.env import CrowdRecommendationEnv

env = CrowdRecommendationEnv(
    feature_path="outputs/features/train_features.npz",
    reward_type="worker",
    episode_length=1000,
    shuffle=True,
    seed=42,
)

state = env.reset()
result = env.step(action=0)
```

其中：

```text
state.shape = [20, 35]
action 是 0 到 19 之间的整数
result.next_state 是下一个 state
result.reward 是当前 action 的 reward
result.done 表示当前 episode 是否结束
result.info 包含 hit、chosen_project_id、positive_project_id 等调试信息
```

可以先用命令行做 smoke test：

```bash
python3 src/env.py \
  --feature_path outputs/features/train_features.npz \
  --reward_type worker \
  --episode_length 5 \
  --steps 8 \
  --seed 42
```

支持的 reward 类型：

```text
worker       使用 worker_rewards
requester    使用 requester_rewards
sum          使用 worker_rewards + requester_rewards
```

后续 `src/train.py` 可以直接使用这个环境训练 DQN。

## 8. 第六步：测试 DQN 模型结构

`src/models.py` 当前包含：

```text
CandidateQNetwork            普通 DQN 网络
DuelingCandidateQNetwork     Dueling DQN 网络
build_model                  模型工厂函数
```

说明：

```text
Double DQN 和普通 DQN 使用同一个网络结构。
二者区别在训练时 target Q 的计算方式，不在模型结构本身。
```

命令行测试：

```bash
python3 src/models.py \
  --model dqn \
  --feature_path outputs/features/train_features.npz \
  --candidate_size 20 \
  --batch_size 4

python3 src/models.py \
  --model double_dqn \
  --feature_path outputs/features/train_features.npz \
  --candidate_size 20 \
  --batch_size 4

python3 src/models.py \
  --model dueling_dqn \
  --feature_path outputs/features/train_features.npz \
  --candidate_size 20 \
  --batch_size 4
```

正常输出中应该看到：

```text
input_shape=(4, 20, 35)
q_shape=(4, 20)
```

这表示模型会为每个 event 的 20 个 candidate project 分别输出一个 Q 值。

## 12. 预处理输出文件说明

### 12.1 project.csv

主要字段：

```text
project_id                 project 编号
project_list_answer_num    project_list.csv 中给出的回答数量
category                   project 一级类别
sub_category               project 子类别
industry                   行业文本

status                     project 状态
start_date                 project 开始时间，UTC ISO 格式
deadline                   project 截止时间，UTC ISO 格式
```

## 17. 常见问题

### 17.1 为什么 worker_quality 负数变成 0？

`worker_quality.csv` 中有些 worker 的质量是 `-1`，这通常表示未知质量。为了让模型可以处理，脚本将其设为：

```text
worker_quality = 0
quality_unknown = 1
```

这样模型既知道质量值不可用，也能区分真实低质量和未知质量。

### 17.2 为什么 score 取 revision 里的最大值？

一个 entry 可能有多个 revision。对于推荐系统来说，我们更关心该 worker 在该 project 上最终能达到的最高质量，因此主实验取：

```text
score = max(revision.score)
```

如果后续要做消融，也可以改成最后一次 revision 的 score 或平均 score。

### 17.3 withdrawn 的 entry 要不要删除？

主实验建议保留。因为 withdrawn 是一个有意义的负面信号，可以用于 requester_reward：

```text
- 0.5 * withdrawn
```

但可以做一个选做消融实验：

```text
保留 withdrawn vs 删除 withdrawn
```

### 17.4 为什么不在预处理中算 worker 历史偏好？

worker 历史偏好必须严格按时间计算。比如在 2018-12-01 的推荐事件里，不能使用 2018-12-05 的提交记录，否则会发生未来信息泄漏。

所以这一步放到 `features.py` 中，按时间流动态更新。`features.py` 会先构造当前 event 的特征，再用当前 event 更新历史统计。
